# Database design

Schema source: `apps/api/prisma/schema/*.prisma`. Migrations: `apps/api/prisma/migrations`. Rules Prisma cannot express (CHECK constraints, triggers, RLS) live in `20261025120100_integrity_rules/migration.sql`.

## Conventions

- **Identifiers:** UUIDv7 (`uuid(7)`, generated by Prisma Client), stored as `uuid`. Time-ordered, so inserts stay index-friendly. `order_status_history.id` is a `bigint` identity because it defines history order.
- **Naming:** models in PascalCase, mapped to snake_case tables and columns. Enums are Postgres enum types in snake_case.
- **Time:** `timestamptz(3)` everywhere, stored in UTC. Organizations default to `Asia/Karachi` for display.
- **Phones:** E.164 (`+92…`), enforced by CHECK. **Emails:** stored lower-case, enforced by CHECK.
- **Controlled states** use enums: user, organization, membership, branch, subscription, rider, order, payment, promotion and notification states.
- **Free-form JSON** is used only for `notifications.payload` (template variables) and `audit_logs.changes` (diffs).

## Entities

| Area                 | Tables                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------- |
| Platform             | `users`, `plans`                                                                                  |
| Tenancy              | `organizations`, `organization_domains`, `memberships`, `branches`, `subscriptions`               |
| Catalog              | `categories`, `products`, `product_variants`, `add_on_groups`, `add_ons`, `product_add_on_groups` |
| Customers & delivery | `customers`, `customer_addresses`, `delivery_zones`, `delivery_zone_areas`, `riders`              |
| Ordering             | `promotions`, `orders`, `order_items`, `order_item_add_ons`, `order_status_history`, `payments`   |
| System               | `notifications` (outbox), `audit_logs` (append-only)                                              |
| Authentication       | `sessions`, `auth_tokens` (see [auth.md](auth.md))                                                |

Notes on modelling choices:

- **Organization = tenant (restaurant brand); branch = physical location.** Menus are organization-wide; orders, delivery zones and riders belong to a branch.
- **Every product has at least one variant**, and prices live only on variants (`Half`/`Full`, `Single`/`Family`, or a single `Regular`). An order item therefore always references exactly one variant. At most one default variant per product (partial unique index).
- **Add-on groups are reusable** across products (`product_add_on_groups`) with `min_select`/`max_select`; a required group has `min_select >= 1`.
- **Customers are per organization**, unique by `(organization_id, phone)`. The same person ordering from two restaurants is two customers; restaurants never see each other's customers.
- **Delivery zones** are defined by area names (how Pakistani addresses work in practice) with an optional radius.
- **Memberships** link users to organizations with a role (`OWNER`, `MANAGER`, `ORDER_STAFF`, `KITCHEN_STAFF`, `RIDER`); `branch_id` optionally limits a member to one branch. Platform-wide roles (`SUPER_ADMIN`, `SUPPORT`) live on `users.platform_role`.
- **Audit logs** are the one table whose `organization_id` is nullable: platform-level events (signup, login) belong to no organization.
- **One current subscription per organization**: partial unique index over `TRIALING`, `ACTIVE`, `PAST_DUE`.
- **Organization domains** map storefront host names to tenants (needed for host-based tenant resolution); one primary domain per organization.
- **`organizations.last_order_number`** provides human-friendly, per-organization order numbers (`UPDATE … RETURNING` inside the order transaction).

## Tenant isolation in the schema

- Every tenant-owned table has `organization_id NOT NULL`, and every tenant-owned table that other rows reference has `UNIQUE (organization_id, id)` (leaf tables such as `customer_addresses` or `order_status_history` do not need it).
- Every reference between tenant-owned rows is a **composite foreign key** `(organization_id, <ref>_id) → parent(organization_id, id)`. A row can only reference rows of its own organization. This covers branch→order, customer→order, zone→order, rider→order, promotion→order, product→order item, order→payment and all catalog relations.
- `order_items (product_id, variant_id) → product_variants (product_id, id)` additionally guarantees the variant belongs to the ordered product.
- All foreign keys are `ON UPDATE RESTRICT`, so changing a parent's `organization_id` can never silently move children into another tenant.
- Payment provider references are unique per organization (`organization_id, method, provider_reference`), so two restaurants with separate merchant accounts never collide or learn about each other's payments.
- Remaining gaps, enforced in the API instead (all rows are already guaranteed to be in the same organization): an order item's add-ons belonging to a group linked to that product, an order's rider and delivery zone belonging to the order's branch, and a payment's collecting rider belonging to the order's branch.

## Money

- All amounts are **integers in minor units** (paisa for PKR) in `*_minor` columns, never floats. `int4` caps a single amount at Rs 21,474,836.47, far above any order or subscription. Use `bigint` sums in reporting queries.
- Each organization has a `currency` (default `PKR`); orders and payments snapshot the currency.
- Rates are **basis points**: `tax_rate_bps` (1600 = 16%), `percent_bps` on promotions.

### Rounding rules

Implemented in `apps/api/src/common/money/money.ts` and `src/modules/orders/domain/order-pricing.ts`, and covered by unit tests.

1. **Line subtotal** = `(unit_price + Σ add-on price × add-on quantity) × quantity`. Exact, no rounding.
2. **Percentage discounts** = `round_half_up(subtotal × bps / 10000)`, then capped by `max_discount_minor` (`percentageDiscount` in `order-pricing.ts`).
3. **Order-level discounts are allocated to lines** in proportion to line subtotals using the **largest-remainder method** (ties go to the earlier line), so `Σ line discounts = order discount` exactly.
4. **Tax is calculated per line** on `line_subtotal − line_discount`, rounded **half up** to the paisa:
   - prices exclusive of tax: `round_half_up(net × rate / 10000)`
   - prices inclusive of tax: `round_half_up(net × rate / (10000 + rate))`. The tax is already inside the price and is not added again.
   - Order tax = Σ line tax.
5. **Delivery fee** is not taxed. A free-delivery promotion is recorded as `delivery_discount_minor`.
6. **Cash rounding (optional):** cash totals may be rounded half up to the nearest rupee. The difference is stored in `rounding_adjustment_minor`, never hidden inside another field. Half-up rounding to the rupee produces −49…+50 paisa; the column CHECK allows −99…99.
7. **Total** = `subtotal − discount + (prices_include_tax ? 0 : tax) + delivery_fee − delivery_discount + rounding_adjustment`.

## Order integrity

Order items snapshot everything needed to reproduce a receipt after the menu changes: `product_name`, `variant_name`, `unit_price_minor`, `quantity`, `add_ons_total_minor`, `line_subtotal_minor`, `discount_minor`, `tax_minor`; `order_item_add_ons` snapshot `group_name`, `name`, `unit_price_minor`, `quantity`. Orders snapshot `tax_rate_bps`, `prices_include_tax`, `promotion_code`, customer name/phone and the delivery address.

Enforced by the database:

| Rule                                                                                                      | Mechanism                                        |
| --------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| Non-negative money, valid ranges, formats                                                                 | CHECK constraints                                |
| `line_subtotal = (unit + add-ons) × quantity`, discount ≤ subtotal                                        | CHECK on `order_items`                           |
| Total formula above                                                                                       | CHECK on `orders`                                |
| Delivery orders have an address; pickup orders have no fee, rider or zone                                 | CHECK on `orders`                                |
| Order subtotal/discount/tax = sums over items; item add-on totals = sums over add-ons; order has ≥ 1 item | Deferred constraint triggers (checked at COMMIT) |
| Latest `order_status_history` entry equals `orders.status`, and history forms a continuous chain          | Deferred constraint trigger                      |
| New orders start in `PENDING`; only allowed transitions; order type is immutable                          | `BEFORE` trigger on `orders`                     |
| `completed_at` / `cancelled_at` / `status_changed_at` stamped on transition; set only for terminal states | Same trigger plus a two-way CHECK                |
| Orders are never deleted (cancel instead)                                                                 | `BEFORE DELETE` / `BEFORE TRUNCATE` triggers     |

Because consistency is checked at commit, an order and its items, add-ons and first history row must be written **in one transaction**. Status changes must lock the order (`SELECT … FOR UPDATE`), update `orders.status` and insert the matching history row in the same transaction; without the lock, two concurrent status changes can commit their history rows out of order and the later commit is rejected.

### Status machine

```
PENDING ──► CONFIRMED ──► PREPARING ──► READY ──► OUT_FOR_DELIVERY ──► DELIVERED      (delivery)
   │            │             │           │            │      ▲
   │            │             │           │            ▼      │
   │            │             │           │       DELIVERY_FAILED ──► CANCELLED
   │            │             │           └──► COMPLETED                              (pickup)
   ├──► REJECTED
   └──► CANCELLED ◄── (from CONFIRMED, PREPARING, READY)
```

The transition table exists in TypeScript (`order-status.ts`) and in the SQL trigger; `order-status.spec.ts` fails if they differ.

## Deletion policy

| Data                                                                                                                                        | Policy                                                                                                                                                                           |
| ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Organizations, branches, customers, riders, promotions, plans                                                                               | `RESTRICT`. Deactivate via status/`is_active`; offboarding is a deliberate process, never a cascade.                                                                             |
| Catalog (categories, products, variants, add-on groups, add-ons, delivery zones)                                                            | Archive with `archived_at`. Hard deletes are `RESTRICT`ed once referenced by an order.                                                                                           |
| Composition children (variants of a product, add-ons of a group, zone areas, customer addresses, order items, item add-ons, status history) | `CASCADE` from their parent. Since orders and referenced products cannot be deleted, this only applies to never-ordered data.                                                    |
| Orders                                                                                                                                      | Never deleted: a trigger rejects `DELETE` and `TRUNCATE`. Cancel instead.                                                                                                        |
| Payments, notifications                                                                                                                     | `RESTRICT` from orders. Financial and delivery records are kept.                                                                                                                 |
| Sessions, auth tokens                                                                                                                       | `CASCADE` from users; invitation tokens also cascade from their membership.                                                                                                      |
| Users                                                                                                                                       | `memberships` cascade; rider links, notification and history actor references are set to `NULL`; audit logs `RESTRICT` (anonymize users with audit history instead of deleting). |
| Audit logs                                                                                                                                  | Append-only: `UPDATE`, `DELETE` and `TRUNCATE` are rejected by triggers.                                                                                                         |

## Indexes

- Foreign-key columns are indexed (Postgres does not do this automatically), including the composite `(organization_id, …)` pairs.
- Query-shaped indexes: orders by `(organization_id, placed_at DESC)`, `(organization_id, branch_id, status, placed_at DESC)`, `(organization_id, customer_id, placed_at DESC)`, `(organization_id, rider_id, status)`; payments by status and time; audit logs by time and entity.
- Partial indexes: one default variant per product, one default address per customer, one primary domain per organization, one current subscription per organization, and the pending-notification queue.

## Supabase hardening

Supabase exposes the `public` schema through its Data API to the `anon` and `authenticated` roles. This app does not use the Data API, so the integrity migration:

- enables RLS on every table with **no policies** (deny all for API roles; the app connects as the table owner and is unaffected);
- revokes all table, sequence and function privileges from `anon` and `authenticated`, including default privileges for future tables and sequences;
- revokes `EXECUTE` on the trigger functions from `PUBLIC`, and removes the global default that would make future functions executable by `PUBLIC`; functions use `SET search_path = ''`.

**Every future migration that creates a table must enable RLS on it.** `pnpm test:integration` fails if any table in `public` lacks RLS or if `PUBLIC` can execute any function.

## Connections and TLS

- Runtime (`DATABASE_URL`): the Supavisor **session pooler** (port 5432) for the long-running API; the transaction pooler (6543) is meant for serverless and is only needed when many instances share the connection limit. Pool size, connection timeout and a statement/query timeout (`DATABASE_STATEMENT_TIMEOUT_MS`) are configured, so a hung query cannot hold a pooled connection indefinitely.
- TLS: node-postgres treats `sslmode=require` as full verification against the system trust store, which does not contain Supabase's CA. The API therefore reads Supabase's CA certificate from `DATABASE_SSL_CA_PATH` and verifies the server certificate; `sslmode` must not appear in `DATABASE_URL` (node-pg would overwrite the CA setting). Production refuses to start without the CA.
- Migrations (`DIRECT_URL`): the Prisma CLI uses this URL only (never `DATABASE_URL`), with `sslmode=verify-full&sslrootcert=<CA file>`. It must be the direct connection or the session pooler, never the transaction pooler (migrations need session-level advisory locks).

## Migration workflow

1. Edit `prisma/schema/*.prisma`.
2. Generate the SQL without touching any database:
   - copy the current `prisma/schema` folder somewhere temporary **before** editing, then run
     `prisma migrate diff --from-schema <copy> --to-schema prisma/schema --script -o prisma/migrations/<timestamp>_<name>/migration.sql`;
   - alternatively `--from-migrations prisma/migrations` with `SHADOW_DATABASE_URL` pointing at a disposable local Postgres (never Supabase).
3. Append what Prisma cannot express (CHECKs, triggers, RLS for new tables) to the same file, and review it.
4. Run `pnpm test:integration`: it applies every migration to an in-memory PostgreSQL 17 and runs the integrity, seed, auth and tenancy suites.
5. Apply to development: `pnpm --filter @app/api db:migrate:deploy`. This applies pending migrations only; it never resets or drops anything. Check with `db:migrate:status`.

Never run `prisma migrate reset`, `prisma migrate dev` or `prisma db push` against Supabase.

## Seed

`pnpm --filter @app/api db:seed -- --target-host=<database host>` creates plans, two `@example.com` users, and a fictional organization (`demo-karahi-house`) with a branch, menu, add-ons, delivery zone, rider, customers, a promotion, one delivered delivery order (with payment and full status history) and one pending pickup order. All names are marked as demo/fictional, and phone numbers use the unassigned `+920000…` range.

- Refuses to run unless `NODE_ENV=development` **and** the host in `DATABASE_URL` is confirmed explicitly with `--target-host=`, so a production URL pasted into `.env` cannot be seeded by accident. Never runs automatically.
- Runs in one transaction (users included); a failure leaves nothing behind.
- Idempotent: plans are upserted; if the demo organization already exists, tenant data is left untouched.
- Orders are priced with the same `priceOrder` function the API will use, so the seed is validated by the database's consistency triggers.

## Known risks and follow-ups

- **Triggers and CHECK constraints are invisible to Prisma.** Prisma will not recreate them, will not show them in `prisma studio`, and `migrate diff` will not report them as drift. Changing an order column referenced by a trigger requires updating the trigger in the same migration.
- **Deferred consistency triggers** run per affected row at commit. Cheap at restaurant order sizes, but bulk imports of orders should be done in batches.
- **Enum changes:** adding a value is safe (`ALTER TYPE … ADD VALUE`); renaming or removing values requires a data migration. Adding an order status also requires updating the transition table in both SQL and TypeScript.
- **Order numbers** use a counter row per organization, which serializes order placement within one organization. Fine at restaurant scale; revisit only if a single tenant exceeds hundreds of orders per second.
- **Payments have `UNIQUE (organization_id, id)`** so future refund records can reference them with a composite foreign key.
- **Not yet modelled (deliberately deferred):** branch opening hours and per-branch product availability (Phases 3–4), rider assignment history and refunds as separate records (Phases 8–9), rider identity documents (sensitive personal data; needs a retention policy first).
